# dp-agt 集群吞吐量与横向扩展能力评估报告

> 架构版本：cluster（控制面 + 无状态 runner，微服务横向扩展）
> 硬件基准：每台 runner 服务器 16 核 / 32 GB，控制面 4 核 / 8 GB
> 数据基准：一次真实 `doc/start` 任务会话样本（已脱敏，端到端 175s，31 轮 LLM，19 次工具调用）
> 上游链路：LLM 网关 → 上游 LLM API（外部服务，单上游，单请求约 5 秒）

---

## 1. 结论摘要

| 维度 | 结论 |
|------|------|
| **横向扩展模型** | N 台 runner × 每台容量 M → 总并发 = N × M。吞吐随 runner 数量**线性增长**，无共享状态瓶颈。 |
| **控制面** | 不随 runner 扩展而成为瓶颈。控制面仅承担路由/渲染/心跳/队列，不跑 SDK，4C/8G 即可。 |
| **上游 LLM 并发上限** | **唯一硬约束。** 必须随 runner 扩容同步提升，否则总并发槽位再多也无意义。 |
| **建议单 runner 配置** | `RUNNER_MAX_CONCURRENT=8`，16C/32G 机器按内存约束承载 8 路。 |
| **建议集群配置** | 2 runner（base）: `max_concurrent_tasks=10`，总并发 10。4 runner（scale）: `max_concurrent_tasks=20`，总并发 20。 |
| **吞吐（2 runner / 10 并发）** | 保守 ~190 次/时；中性 ~300 次/时；乐观 ~540 次/时 |
| **吞吐（4 runner / 20 并发）** | 保守 ~380 次/时；中性 ~600 次/时；乐观 ~1080 次/时 |
| **业务口径（公文）** | 每篇公文平均触发 **K 道** agent 入口（当前业务实测 K = 5），2 runner 折合 **38~108 篇/时**，4 runner 折合 **76~216 篇/时**。 |

> 关键定性：dp-agt 改为控制面 + runner 微服务架构后，执行层完全无状态、可水平扩展。所有重活（LLM 推理、文档解析、核稿）都在外部服务，runner 只承担「同时跑 M 个 agent 子进程」这一件事。因此**吞吐天花板不在 dp-agt 内部，而在上游 LLM 的并发能力**。

### 1.1 客户侧容量规划（按目标公文处理能力反推）

## 2. 集群架构与职责边界

```
外部系统/管理员 ──▶ 控制面（1 台，4C/8G）
                     │  路由 / 鉴权 / 渲染 / SQLite / 队列 / 选路
                     │  :20001 (HTTPS)
                     │
                     │  :21001 (HTTPS + Bearer)
                     ▼
              ┌──────┴──────────────┐
              ▼                     ▼
    runner-1（16C/32G）    runner-2（16C/32G）   … 按需扩展
    · 跑 Agent 子进程       · 跑 Agent 子进程
    · 无状态               · 无状态
    · :21001               · :21001
              │                     │
              └─────────┬───────────┘
                        │ 出站
                        ▼
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼
     LLM 网关      文件服务        审稿服务
     (外部)        (外部)          (外部)
```

- **控制面**：轻量调度，不运行 SDK。只做路由鉴权、提示词渲染、任务队列、runner 选路和状态落库。
- **runner**：无状态执行节点。接收派发 → 跑 agent 子进程 → 逐帧回传。不读 SQLite / prompts / secrets。
- **回调**：由 agent 子进程自行完成，不经过控制面或 runner 投递。
- **同 linkid** 全局串行（由控制面 `linkChains` 保证），同 linkid 的任务永远路由到同一台 runner（session 亲和）。

## 3. 横向扩展模型

### 3.1 基本公式

```
集群总并发数 = Σ(每台 runner 的 RUNNER_MAX_CONCURRENT)
总吞吐（次/时）= 集群总并发数 × 3600 ÷ 单任务平均耗时（秒）
```

runner 之间**无共享状态、无相互依赖**，增加 runner 即可线性增加总并发，无需协调。

### 3.2 控制面是否成为瓶颈

| 工作 | 并发特征 | 资源消耗 |
|------|---------|---------|
| HTTP 路由 / 鉴权 | 每请求一次 | 极轻（Express） |
| 队列操作 | 每任务一次入队 + 一次收尾 | 内存标记 |
| 提示词渲染 | 每任务一次（~10ms 字符串替换） | 忽略 |
| runner 心跳 | 每 5s 一轮（每 runner 一次 /status） | 忽略 |
| runner 派发 | 每任务一次 POST /run | HTTP 客户端，内存标记 |
| SSE 消息代理 | 每帧一条转发 | 低负载 |

控制面本身**不执行 SDK**、不做文档解析、不调用 LLM，所有重计算被 runner 承担。吞吐瓶颈不在此层。

### 3.3 扩展建议

| 阶段 | runner 数 | 单 runner 并发 | 集群总并发 | 上游 LLM 并发需求 |
|------|----------|--------------|----------|-----------------|
| 初始 | 2 | 5 | **10** | ≥10 路 |
| 常规 | 2 | 8 | **16** | ≥16 路 |
| 扩展 | 4 | 8 | **32** | ≥32 路 |
| 长尾 | N | 可配 | **N × M** | ≥ N × M 路 |

> 注意：控制面 `max_concurrent_tasks` 需要 ≥ 集群总并发数，否则控制面自己会成为闸门。建议 `max_concurrent_tasks` = 集群总并发数 + 少量余量。

## 4. 吞吐量模型

```
吞吐（次任务/时） = 集群总并发数 × 3600 ÷ 单任务平均耗时（秒）

上游 LLM 在途请求（峰值） ≈ 总并发数（每并发同一时刻最多 1 路 LLM）
```

> 单任务耗时的构成：`LLM 时间 ≈ N × 5s`（N=30 时约 150s）＋ 工具等待时间（下载/OCR/审稿/回调，约 40%）。实测样本端到端 175s 与此一致，故中性档取 120~175s。

### 4.0 业务模型（从业务到工程的换算基础）

每篇公文的处理链路、每步的资源消耗，统一用以下业务变量描述：

| 变量 | 取值 | 说明 |
|------|------|------|
| **K** | 5 | 每篇公文平均触发 agent 调用次数（业务实测，`/api/v1/doc/*` 入口） |
| **N** | 30 | 单次 agent 调用完成任务所需的 LLM 轮数（turn）。实测 trace 中未完成任务为 10~22 轮，完整任务约 30 轮 |
| **单次 agent 输入 token** | ~10000 | 30 轮累计；首次输入 ~5000（含 prompt + CLAUDE.md + tools schema），中间轮次较小 |
| **单次 agent 输出 token** | ~2000 | 30 轮累计；末次输出 ~1000（最终结果 JSON），中间轮次较小 |
| **每轮 LLM 响应** | < 5s | 上游 LLM 实测 |

**由此推导：**

```
单次 agent 总 token ≈ 10000 + 2000 = 12000 token
单篇公文总 token = K × 12000 = 5 × 12000 = 60000 token（50000 in + 10000 out）
```

**上游 LLM 的 token 吞吐需求**（对上游提要求时用）：

```
上游 token 吞吐（tokens/s）≈ 集群总并发数 × 单次 agent 总 token ÷ 单任务耗时
```

按中性 120s/任务、单 agent 12000 token 计，每并发约 100 tokens/s；档位 A（24 并发）约 2400 tokens/s，档位 B（168 并发）约 16800 tokens/s。

> 5000/1000 是每轮 LLM、10000/2000 是每次 agent（30 轮累计）。下文「单次 agent」均指后者。

### 4.1 业务口径换算（公文数）

每篇公文平均触发 agent 入口的次数记为 **K**（当前业务实测 K = 5，指每篇公文平均触发 5 次 `/api/v1/doc/*` 入口）。换算：

```
公文节点处理能力（篇/时） = 任务吞吐（次/时） ÷ K
```

K 是业务侧变量，随流程环节增减而变；下表按当前 K = 5 计算。

### 4.2 各规模吞吐对照

| 集群规模 | 总并发 | 保守（175s） | 中性（120s） | 乐观（60s） |
|---------|-------|-------------|-------------|------------|
| 1 runner × 5 | 5 | 103 次/时 · 21 篇/时 | 150 次/时 · 30 篇/时 | 300 次/时 · 60 篇/时 |
| 2 runner × 5 | 10 | 205 次/时 · 41 篇/时 | 300 次/时 · 60 篇/时 | 600 次/时 · 120 篇/时 |
| 2 runner × 8 | 16 | 330 次/时 · 66 篇/时 | 480 次/时 · 96 篇/时 | 960 次/时 · 192 篇/时 |
| 4 runner × 8 | 32 | 660 次/时 · 132 篇/时 | 960 次/时 · 192 篇/时 | 1920 次/时 · 384 篇/时 |

> 保守 = 实测 175s（扫描件异常路径）；中性 = 120s（多数任务，无扫描件异常）；乐观 = 60s（轻任务如 route/fill）。
> 上表「篇/时」按 K = 5 折算；若业务侧 K 变化，用 `任务吞吐 ÷ K` 重新换算即可。

## 5. 实测数据基础（不变）

样本：一次真实 `doc/start`（收文流程启动）任务会话。

| 指标 | 实测值 | 说明 |
|------|--------|------|
| 端到端耗时 | **175 秒** | 从任务入队到输出最终 JSON |
| LLM 请求轮数 | **31 轮** | 含异常路径的多次自我修正 |
| 工具调用次数 | 19 次 | 下载、格式探测、解压、文本提取、OCR、回调 |
| LLM 时间占比 | ≈ 60% | 其余为工具等待（OCR 最重） |

### 5.1 该样本为何偏「重」

- 文件名为 `.doc`，实际是 `.docx`（ZIP），首次解析返回空文本
- 环境缺部分命令行工具，多种提取命令逐一试错
- 正文实为**扫描件**（3 页图片），最终只能逐页 OCR

由此带来的结论不变：**agent 任务遇到异常会天然多打若干轮 LLM 自我修正**，单任务 LLM 轮数可能显著高于「理想路径」。吞吐估算必须为此留余量。

## 6. 单 runner 资源配置

### 6.1 内存与 CPU

| 资源 | 并发 5 | 并发 8 | 16C/32G 是否够 |
|------|--------|--------|--------------|
| 内存 | 5 × ~500 MB ≈ 2.5 GB + 系统 ≈ 4 GB | 8 × ~500 MB ≈ 4 GB + 系统 ≈ 6 GB | **富余** |
| CPU | agent 子进程大部分时间等网络 I/O，非 CPU 密集 | 同左 | **富余** |

> runner 是「I/O 密集 + 内存密集」，不是 CPU 密集。每个 agent 大部分时间在等 LLM 响应（每轮 ~5s）和工具返回（下载/OCR/审稿/回调），CPU 真实利用率低。给 16C/32G 即可，32C 属于浪费；不必按 CPU 核数来算并发，而是按内存（每并发 ~500 MB）来算。
> runner 不读 SQLite、不存 trace（逐帧流回控制面），内存比旧单实例更省。

### 6.2 可平滑升级

单 runner 的 `RUNNER_MAX_CONCURRENT` 根据**内存**（每并发 ~500 MB）确定，而非 CPU 核数：

| 机器规格 | 建议并发 | 依据 |
|---------|---------|------|
| 8C / 16G | 5 | 5 × 500 MB = 2.5 GB，内存余量足 |
| **16C / 32G** | **8** | 8 × 500 MB = 4 GB，内存富余；CPU 足够 |
| 32C / 64G | 16~20 | 内存可到 10 GB；CPU 仍非瓶颈 |

## 7. 上游 LLM 并发要求

LLM 网关将请求原样透传到上游。上游一旦拒流（429/503/超时），错误会**直接穿透到 agent 任务，变成 `failed`**。

| 集群总并发 | 上游最低并发 | 建议并发（留余量） | 上游 token 吞吐（中性 120s） |
|-----------|------------|-----------------|---------------------------|
| 10 | ≥10 路 | 16 路 | ~1000 tokens/s |
| 16 | ≥16 路 | 24 路 | ~1600 tokens/s |
| 32 | ≥32 路 | 48 路 | ~3200 tokens/s |
| N × M | ≥ N × M 路 | N × M × 1.5 路 | N×M × 100 tokens/s |

> 计算：每并发一次 agent 12000 token ÷ 120s ≈ 100 tokens/s。
> **给上游提要求的建议口径**：对 LLM 网关所使用的上游地址，开放 ≥ 集群总并发数（建议 1.5 倍）路并发流式请求，单请求约 5 秒；同时满足对应档位的 token 吞吐（见上表末列）。理由：下游 N × M 个 agent 子进程并发运行时，峰值会同时打向上游。

## 8. 瓶颈识别

| 环节 | 是否瓶颈 | 说明 |
|------|---------|------|
| **控制面** | 否 | 轻量调度，不跑 SDK，4C/8G 足够 |
| **runner（单台）** | 否 | 无状态执行，I/O 密集 + 内存密集，非 CPU 密集；按并发数线性扩 |
| **runner（集群）** | 否 | 加机器即可线性扩容 |
| LLM 网关 | 否 | 纯转发 |
| 文件服务（doc-util） | **需注意** | OCR 并发上限默认 4，扫描件多时可能成为瓶颈（见 §8.1） |
| 审稿服务（rd-cli） | **需注意** | 内置 agent + LibreOffice，review 任务资源开销大（见 §8.1） |
| **上游 LLM 并发上限** | **是（唯一硬约束）** | 必须随 runner 扩展同步提升 |
| 同 linkid 串行 | 业务约束 | 决定「总并发」的真实利用率上限 |

### 8.1 配套服务

| 服务 | CPU | 内存 | 并发/容量 | 说明 |
|------|-----|------|-----------|------|
| LLM 网关 | 1~2 核 | 256 MB 级 | 无并发上限 | 纯转发，几乎无负载 |
| 文件服务 | **8 核** | **16 GB** | 默认 4 路 OCR，建议 8~16 | 扫描件识别 CPU 密集（ONNX Runtime），每路 OCR 约 1~2 GB 内存 |
| 审稿服务 | **8 核** | **16 GB** | 单实例内置 agent + LibreOffice | review 任务专用，LibreOffice 转换大文档时内存消耗大 |

## 10. 部署配置汇总

| 服务名称 | 台数 | 资源配置（单台） | 部署方式 | 关键参数 |
|----------|------|-----------------|---------|---------|
| 控制面 | 1 | 4C / 8G / 500GB | 单实例 | `max_concurrent_tasks=集群总并发` |
| runner | 2~N | **16C / 32G / 100GB** | 每台独立部署 | `RUNNER_MAX_CONCURRENT=8`（内存约束，非 CPU） |
| LLM 网关 | 1 | 2C / 4G / 200GB | 独立部署 | 无需调整 |
| 文件服务 | 1 | **8C / 16G / 500GB** | 独立部署 | `MAX_CONCURRENT_CONVERSIONS=8~16` |
| 审稿服务 | 1 | **8C / 16G / 500GB** | 独立部署 | 单实例 |

**上游 LLM API 要求**（外部资源）

| 项目 | 要求 | 说明 |
|------|------|------|
| 并发流式请求 | ≥ 集群总并发数（建议 1.5×） | 随 runner 扩展同步提升 |
| 单请求响应时间 | 约 5 秒 | 当前上游实测值 |
| 协议 | Anthropic 兼容 | 经 LLM 网关转发 |

## 11. 监控与验证

| 指标 | 来源 | 用途 |
|------|------|------|
| `sdk_run_complete` 的 `durationMs` 分布 | 控制面日志 | 校准单任务平均耗时 |
| 峰值 `processing` 并发数 | 控制面 `getRunningCount()` | 验证集群并发是否吃满 |
| 各 runner `/status` 的 `running_count` | 心跳日志 | 验证各节点负载均衡 |
| runner 总 RSS | 系统监控 | 验证内存余量 |
| LLM 网关在途请求数 | 网关日志 | 验证上游并发是否打满 |
| 上游 LLM 429/503 频次 | 控制面错误日志 | 发现上游并发不足的信号 |

## 12. 附录：关键假设

- 单 LLM 请求约 5 秒（用户提供）。
- 单 agent 子进程 RSS 约 500 MB（经验值）。
- 单任务 LLM 轮数约 31 轮、LLM 时间占比约 60%（来自一份 `doc/start` 实测样本，异常路径偏重，故吞吐区间取保守到乐观三档）。
- 上游 LLM 为外部服务，须随集群扩展同步提并发。
- runner 之间完全无状态、无共享，横向扩展不引入额外一致性开销。
- 控制面保持单实例，集群模式下不做控制面 HA。
