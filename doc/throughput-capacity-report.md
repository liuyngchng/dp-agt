# dp-agt 生产部署吞吐量与并发量评估报告

> 评估对象：单实例 dp-agt（`node dist/index.js`）
> 硬件基准：32 核 CPU / 64 GB 内存的单台 PC，仅部署 dp-agt
> 数据基准：现有代码配置默认值 + 一次真实 `doc/start` 任务会话样本（已脱敏）
> 上游链路：api-gate（纯协议转发）→ 上游 LLM API（单上游，单请求约 5 秒）
> 配套服务（独立部署，不在本机）：api-gate、doc-util、rdCLI

---

## 1. 结论摘要

| 维度 | 结论 |
|------|------|
| **本机硬件（32C/64G）** | 不是瓶颈。16 并发仅需约 8~12 GB 内存，CPU 大量空闲。 |
| **api-gate** | 不是瓶颈。Go 无状态纯转发，无并发上限，几百路无压力。 |
| **上游 LLM 并发上限** | **唯一硬约束。** 必须 ≥16 路（建议 32 路），否则突发时任务成批失败而非变慢。 |
| **建议并发配置** | `max_concurrent_tasks = 16`，`max_pending_tasks = 128`。 |
| **预期吞吐（16 并发）** | 保守 ~330 次任务/时；中性 ~480 次/时；乐观 ~960 次/时。 |
| **业务口径（公文）** | 每篇公文平均触发 **5 道** agent 节点，折合约 **66~192 篇公文/时**（中性 ~96 篇/时）；同一时刻**最多 16 篇公文**处于 agent 处理中。 |
| **部署规模** | 共 **8 台服务器**（4 主 + 4 冷备）：dp-agt、api-gate、doc-util、rd-cli 各一主一备；合计 **100 核 / 168 GB**。 |

> 关键定性：dp-agt 是「薄网关 + 并发跑 Claude Code 子进程」。所有重活（LLM 推理、文档解析、核稿）都在别的机器上，本机只承担「同时跑 N 个 agent 任务」这一件事，且 agent 大部分时间在等网络 I/O。因此**吞吐量的天花板不在本机，而在上游 LLM 的并发能力**。

---

## 2. 部署拓扑与职责边界

```
OA/外部系统 ──▶ dp-agt（本机，32C/64G）
                   │  校验 + 写 SQLite + 入队 + 立即返回 task_id
                   │  异步并发跑 N 个 Claude Code 子进程
                   │
                   ├──▶ api-gate（独立机器） ──▶ 上游 LLM API（单上游）
                   ├──▶ doc-util（独立机器）      文档解析 / 格式转换
                   └──▶ rdCLI（独立机器）        自动核稿（仅 review 任务用）
```

- dp-agt 本身**不做业务逻辑**，只做：路由鉴权、提示词渲染、任务队列、并发调度、SDK 调用与状态落库。
- 回调由 Agent 子进程自行 `curl` 完成，不经过 dp-agt 投递。
- 同一 `linkid`（同一篇公文）**严格串行**，不同 `linkid` 之间并发，受 `max_concurrent_tasks` 限制。

## 3. 吞吐量模型

```
吞吐（次任务/时） = 并发数 × 3600 ÷ 单任务平均耗时（秒）

上游 LLM 在途请求数（均值） = 并发数 × 单任务 LLM 时间占比
上游 LLM 在途请求数（峰值） ≈ 并发数（突发时多任务同时进入 LLM 阶段）
```

两个关键点：

1. **「并发数」≠「同时打向上游 LLM 的请求数」。** agent 任务在「等 LLM」和「跑工具」之间交替，跑工具（下载、解析、轮询、回调）期间不占用 LLM。
2. **吞吐的单位是「agent 任务」，不是「办结公文」。** 一篇公文办结要过多道 agent 节点，中间还隔着人工审批时间；dp-agt 只是其中的几拍。

### 3.1 业务口径换算（公文数）

一篇公文从收文到办结，会在多个环节触发 dp-agt 的 agent 任务。以收文主流程为例：

```
start[1] 启动收文 → fill_doc_info[2] 信息填充 → get_office_info[3] 拟办意见
      → route 流转识别（送领导批示） → get_output_dept[4] 承办部门
      → route 流转识别（部门办结） → 办结
```

`route` 会在多个流转环节反复触发，`review` 属于发文流程。按业务实测，**一篇公文平均触发约 5 道 `/api/v1/` 入口**（本报告采用该值）。

**换算公式**

```
公文节点处理能力（篇/时） = 任务吞吐（次/时） ÷ 每篇公文的 agent 节点数（取 5）
```

**换算结果（16 并发，每篇 5 道）**

| 档位 | 任务吞吐（次/时） | 公文处理能力（篇/时） |
|------|-------------------|-----------------------|
| 保守（实测 175s/任务） | 330 | **66 篇/时** |
| 中性（120s/任务） | 480 | **96 篇/时** |
| 乐观（60s/任务） | 960 | **192 篇/时** |

**两个必须澄清的口径**

1. 上表度量的是 **「agent 节点处理能力」**——即 dp-agt 每小时能消化多少篇公文「各走一遍某道节点」的处理量，**不是「办结公文数/时」**。
2. 公文真正「办结」的速度由 **OA 人工审批节奏**主导（节点之间等人，短则分钟、长则天级）。dp-agt 只在公文命中某个 agent 节点时短暂占用并发槽位，等待期间并发为 0。因此 16 并发对应的业务容量是：**同一时刻最多 16 篇公文正处于 agent 处理中**。

> 结论：dp-agt 的节点处理能力约 **66~192 篇/时**（中性 ~96 篇/时，每篇按 5 道节点折算）；而「每小时办结多少份公文」是 OA 流程节奏决定的，不由此报告的上限决定。

## 4. 实测数据基础

样本：一次真实 `doc/start`（收文流程启动）任务会话，已过滤 SDK `[system]` 消息。

| 指标 | 实测值 | 说明 |
|------|--------|------|
| 端到端耗时 | **175 秒（≈2.9 分钟）** | 从任务入队到输出最终 JSON |
| LLM 请求轮数 | **约 16 轮** | 含多轮「工具结果异常 → 变招重试」的探索 |
| 工具调用次数 | 约 19 次 | 下载、格式探测、解压、文本提取、OCR、回调×2 |
| LLM 时间占比 | ≈ 60% | 其余为工具等待 |
| 工具时间占比 | ≈ 40% | 其中 OCR 等待最重（单次 8~25 秒） |

### 4.1 该样本为何偏「重」

这条路径属于**异常路径**，不能代表所有任务，但真实且常见：

- 文件名为 `.doc`，实际是 `.docx`（ZIP），首次解析返回空文本；
- 环境缺 `python3`，多种文本提取命令逐一试错；
- 正文实为**扫描件**（3 页图片），最终只能逐页 OCR。

由此带来的结论是：**agent 任务遇到异常会天然多打若干轮 LLM 自我修正**，单任务 LLM 轮数可能显著高于「理想路径」。吞吐估算必须为此留余量。

## 5. 并发量与吞吐分析（16 并发）

### 5.1 内存与 CPU（本机）

| 资源 | 16 并发占用 | 64G/32C 是否够 |
|------|-------------|----------------|
| 内存 | 16 × ~500 MB/子进程 ≈ 8 GB；加 Node 父进程、SDK trace 缓存、OS ≈ 12 GB 量级 | **富余** |
| CPU | agent 子进程大部分时间等网络 I/O，非 CPU 密集 | **富余** |

> 次要观察：`sdk-runner.ts` 会把整条 SDK 消息流缓存在父进程内存，任务结束才落库（`sdk_traces` 表）。重任务（review）的 trace 可达数十 MB，并发进一步抬升时需留意父进程内存，但 16 并发下不构成瓶颈。

### 5.2 吞吐估算

按「单任务平均耗时」三档给出区间：

| 档位 | 单任务耗时假设 | 16 并发吞吐 |
|------|----------------|-------------|
| 保守（以实测 175s 为基准） | 175 秒 | **≈ 330 次/时** |
| 中性（多数任务无扫描件异常） | 120 秒 | **≈ 480 次/时** |
| 乐观（轻任务如 route/fill） | 60 秒 | **≈ 960 次/时** |

### 5.3 上游 LLM 在途请求

单任务 LLM 占比 ≈ 60%：

| 指标 | 估算值 |
|------|--------|
| 均值 | 16 × 60% ≈ **10 路** |
| 峰值 | **≈ 16 路**（早高峰多篇公文同时入队时，首轮 LLM 请求几乎同时发出） |

## 6. 上游 LLM 并发要求（核心结论）

api-gate 本身不设并发上限、不做重试、不改状态码，会把 dp-agt 发来的请求**原样透传**到上游。因此上游一旦拒流（429/503/超时），错误会**直接穿透到 agent 任务，变成任务 `failed`**——中间没有任何一层会兜底。

| 上游 LLM 并发上限 | 效果 |
|------------------|------|
| < 8 路 | 稳态都不够，任务排队等 LLM，吞吐被压 |
| 8~12 路 | 稳态够、突发峰值会排队，偶发延迟 |
| **≥ 16 路** | 突发峰值也接得住，16 并发能跑满 |
| **32 路（建议）** | 留一倍余量，并为未来把 `max_concurrent_tasks` 提到 32 留空间 |

> **给上游提要求的建议口径**：对 api-gate 所使用的上游地址，开放 ≥16 路（建议 32 路）并发流式请求，单请求约 5 秒。理由：下游单次会突发 16 路并发流。

## 7. 配置建议

| 配置项 | 当前默认 | 建议值 | 理由 |
|--------|---------|--------|------|
| `max_concurrent_tasks` | 5 | **16** | 本机 32C/64G 富余，16 并发约 8~12 GB 内存 |
| `max_pending_tasks` | 10 | **128** | 该值是「running + pending」总在途上限，作为背压阀；设小会在突发时 503 回压给 OA（OA 不重试 = 丢任务） |
| `llm.timeout_ms` | 600000 | 保持不变 | 滑动无活动超时语义，勿改回 wall-clock |

> 注意：`max_concurrent_tasks` 设多少，取决于「峰值同时有多少**不同**公文命中 agent 节点」。同一 `linkid` 串行，16 并发只有在「同时在处理的公文 ≥16 篇」时才吃得满；若实际并发公文数长期 <16，设 16 还是 32 都不影响吞吐。

## 8. 瓶颈识别与前提条件

| 环节 | 是否瓶颈 | 说明 |
|------|---------|------|
| dp-agt 本机（32C/64G） | 否 | 16 并发资源富余 |
| api-gate | 否 | 纯转发，无并发上限 |
| doc-util | **需注意** | 内置 OCR 并发上限默认 4（`MAX_CONCURRENT_CONVERSIONS`），扫描件任务并发高时可能排队（见 §8.1） |
| rdCLI | **需注意** | 内置 Claude Code + LibreOffice，`review` 任务内存/CPU 开销大（见 §8.1） |
| **上游 LLM 并发上限** | **是（唯一硬约束）** | 必须 ≥16 路（建议 32 路） |
| 同 linkid 串行 | 业务约束 | 决定「并发数」的真实利用率上限 |

### 8.1 配套服务资源需求

三个配套服务均为 Docker 部署，与 dp-agt 同处 `llm_net` 内网，但各自独立部署（不在本机）。以下是资源需求评估：

| 服务 | CPU | 内存 | 并发/容量 | 说明 |
|------|-----|------|-----------|------|
| **api-gate** | 1~2 核 | 256 MB 级 | 无并发上限 | Go 无状态纯转发，16 并发下几乎无负载 |
| **doc-util** | 4~8 核 | 4~8 GB | **默认 4 路 OCR 并发** | 集成 OpenCV + ONNX Runtime OCR，扫描件识别是 CPU/内存密集 |
| **rd-cli** | 4~8 核 | 4~8 GB | 单实例内置 Claude Code + LibreOffice | `review` 任务拉起 Claude Code 子进程 + LibreOffice 转换，重任务开销大 |

**关键提示**

1. **doc-util 是真正的隐藏瓶颈**：`cmd/server/main.go` 的 `maxConcurrentConversions()` 默认 **4**，`/extract/txt`、`/convert/*` 全部过 `limit()` 信号量，超过 4 路并发直接返回 **429**。扫描件（如 §4 实测样本的 3 页图片）走 OCR，单次耗时 8~25 秒。若 16 个 dp-agt 任务中多篇是扫描件，会在这里排队甚至 429 失败。**建议把 `MAX_CONCURRENT_CONVERSIONS` 提到 8~16**，并按机器核数给足内存（OCR 每路约 1~2 GB 峰值）。

2. **rd-cli 是重任务专用**：只有 `review`（发文审核）走 rdCLI，且它内部会拉起 Claude Code 子进程（自己还要经 api-gate 打上游 LLM）+ LibreOffice 做 `.doc→.docx`。它消耗的不只是 CPU/内存，还会**额外占用上游 LLM 并发**。好在 review 任务占比低（混合场景 ~20%），16 并发下同一时刻同时跑 review 的通常只有 1~3 个。

3. **doc-util 内置 2 GB 缓存**（`CACHE_MAX_MB=2048`，TTL 7 天）：相同文档重复命中不必重新 OCR，对吞吐有利，但意味着要预留 ~2 GB 额外内存给缓存。

> 结论：api-gate 资源可以给到最小；doc-util 和 rd-cli 各按「4~8 核 + 4~8 GB」起配，并优先把 doc-util 的 OCR 并发上限（`MAX_CONCURRENT_CONVERSIONS`）从默认 4 调高到 8~16，否则扫描件公文一多，doc-util 会先于 dp-agt 成为瓶颈。

### 8.2 前提条件

以上分析和配套服务配置同时满足时，吞吐量才能达到 §3.1 的预期值：

1. 上游 LLM 对 api-gate 地址开放 **≥16 路**并发流式请求。
2. doc-util 的 `MAX_CONCURRENT_CONVERSIONS` 提至 **≥8**（避免扫描件排队产生 429）。
3. 峰值时确有 ≥16 篇不同公文同时命中 agent 节点。
4. rd-cli 所在机器的 CPU/内存不成为 review 任务瓶颈。

## 9. 部署配置汇总

| 服务名称 | 功能 | 服务器台数 | 资源配置（单台） | 部署方式 | 服务建议参数 |
|----------|------|-----------|-----------------|---------|--------------|
| dp-agt | AI 数字员工 | 2 | 32C / 64G / 500GB | 一主一冷备 | `max_concurrent_tasks=16`、`max_pending_tasks=128` |
| api-gate | LLM 网关 | 2 | 2C / 4G / 50GB | 一主一冷备 | 无需调整 |
| doc-util | 文档解析 | 2 | 8C / 8G / 500GB | 一主一冷备 | `MAX_CONCURRENT_CONVERSIONS=8~16` |
| rd-cli | 文档审核 | 2 | 8C / 8G / 500GB | 一主一冷备 | 单实例（review 任务专用） |

**冷备说明**：各服务均为一主一冷备。冷备机与主机同配置、平时不承载流量，故障时手动切换并启动；**不做有状态数据/会话迁移**（切换后以全新状态运行）。

**上游 LLM API 要求**（外部资源，非自建服务器）

| 项目 | 要求 | 说明 |
|------|------|------|
| 并发流式请求 | **≥16 路（建议 32 路）** | 16 个 agent 并发时峰值会冲到 16 路，32 路留一倍余量 |
| 单请求响应时间 | **约 5 秒**（首 token / 整轮输出） | 当前上游实测约 5s，是本报告吞吐估算的基础 |
| 协议 | Anthropic 兼容（经 api-gate 转 OpenAI `/chat/completions`） | 单上游、单模型，无负载均衡 |

**汇总**

- 服务器总台数：**8 台**（4 主 + 4 冷备）。
- 资源配置合计（含冷备）：**100 核 / 168 GB / 约 3 TB 磁盘**。
- 上游 LLM API 为外部资源，不在上述 8 台内，但对 api-gate 地址需满足上表要求；其中**并发数是全部配置里唯一的硬约束**。

## 10. 监控与验证指标

上线后建议盯以下指标，把估算收敛成实测值：

| 指标 | 来源 | 用途 |
|------|------|------|
| `sdk_run_complete` 的 `durationMs` 分布 | dp-agt 日志 | 校准「单任务平均耗时」，修正吞吐区间 |
| 每任务 LLM 轮数（`type: assistant` 消息数） | `sdk_traces` 表 | 校准「LLM 时间占比」，修正上游并发需求 |
| 峰值 `processing` 并发数 | `getRunningCount()` / 日志 | 验证 16 并发是否吃得满 |
| dp-agt + 子进程总 RSS | 系统监控 | 验证内存余量（勿超 ~50G） |
| api-gate 在途请求数 | api-gate 日志 | 验证上游并发是否打满 |

## 11. 附录：关键假设清单

- 单 LLM 请求约 5 秒（用户提供）。
- 单 Claude Code 子进程 RSS 约 500 MB（经验值，需以实际监控校准）。
- 单任务 LLM 轮数约 16 轮、LLM 时间占比约 60%（来自一份 `doc/start` 实测样本，异常路径偏重，故吞吐区间取保守到乐观三档）。
- 上游 LLM 为单上游、单模型，无负载均衡（现状约束，已接受）。
- dp-agt 单实例部署，内存队列状态为权威（见既有设计约定）。
